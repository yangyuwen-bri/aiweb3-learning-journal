# Agent Memory：跨时间的意图与状态管理

日期：2026-05-25
状态：分享会课件整理 + 个人理解

## 1. 一句话理解

今天这份课件最重要的观点是：

```text
Agent Memory 不是更大的上下文窗口，而是一个跨时间管理意图和状态的系统。
```

用户一开始给出的目标通常是不完整的。真正可执行的任务状态，是在澄清、选择、工具调用、结果验证和产物迭代中逐步形成的。

所以 memory 的价值不是把所有历史都塞回模型，而是让下一轮对话或下一次工作可以从“已经形成的有效状态”继续。

## 2. 为什么需要 Agent Memory

没有 memory 时，每次新会话都像重新开始：

- 用户要重新解释目标。
- 系统要重新推断限制条件。
- 之前做过的选择和中间结论容易丢失。
- 未完成的工作很难自然继续。

有用的 memory 应该把“上次已经解决的问题”保留下来：

- 目标和优先级
- 用户偏好
- 已经做出的取舍
- 项目规则
- 工具命令
- 已验证或失败过的尝试
- 下一步应该从哪里继续

我的理解：

```text
好的 memory 不是保存全部历史，而是减少下一次继续工作时的重建成本。
```

## 3. 产品视角：Restart vs Resume

课件把 memory 的产品价值拆成一个很清楚的对比：

| 状态 | 用户体验 | 本质问题 |
| --- | --- | --- |
| Restart | 每次都像第一次见面 | 用户要重复交代背景 |
| Resume | 从上次有效状态继续 | 系统带回当前需要的状态 |

这对学习 agent 很重要。一个学习 agent 如果每次都忘记学习者的目标、水平、偏好、已经完成的任务和薄弱概念，就只能做临时问答。

如果它能记住这些状态，就可以更像一个长期陪伴的学习系统。

## 4. 两类常见产品记忆

课件用了 ChatGPT 和 Claude Code 两个例子说明：不同产品要记住的东西不一样。

### ChatGPT：用户连续性

ChatGPT 类聊天产品更关注用户连续性：

- 稳定偏好，例如语言风格、常用输出方式、学习目标
- 有用的过往上下文
- 用户可见、可删除、可暂停的控制权

它解决的是：

```text
这个助手是否还记得“我是谁、我偏好什么、我之前说过什么”？
```

### Claude Code：项目连续性

Claude Code 类 coding agent 更关注项目连续性：

- build / test / lint 命令
- repo 结构和代码约定
- 已经踩过的坑
- 之前做出的技术决策
- 不应该重复尝试的失败路径

它解决的是：

```text
这个 agent 是否还记得“这个项目如何工作、上次做到哪里、哪些约束已经确认过”？
```

## 5. Memory 会随着 Agent 能力升级

课件里有一个关键判断：

```text
Product memory changes with agency.
```

如果 AI 只是聊天，memory 主要让回答更顺滑。

但当 agent 开始使用工具、修改文件、调用 API、处理钱包或执行真实任务时，memory 就不只是便利功能，而会影响 agent 下一步做什么。

这时 memory 会变成控制层：

- 记错可能导致错误行动。
- 过期状态可能导致错误判断。
- 不该保存的内容可能带来隐私和安全风险。
- 不该返回的内容可能污染当前决策。

所以 agent 越能行动，memory 越需要被设计、审计和控制。

## 6. 三个动词：Recall、Retrieve、Revise

课件特别区分了三个容易混在一起的词。

### Recall：用户看到的记起效果

Recall 是产品层的表现。用户感觉系统“记得我之前说过的东西”。

它回答的是：

```text
用户感受到的连续性是什么？
```

### Retrieve：系统把记忆取回当前上下文

Retrieve 是系统操作。系统根据当前任务，把相关记忆取出来，放进当前上下文。

它回答的是：

```text
现在这一步需要返回哪些已保存状态？
```

### Revise：修改持久记忆

Revise 是更新记忆。新证据出现后，旧记忆可能要被修正、合并、降级或删除。

它回答的是：

```text
什么内容已经不再准确，应该被更新？
```

我的理解：

```text
Recall 是用户看到的效果，Retrieve 是当前使用记忆，Revise 是长期维护记忆。
```

## 7. Memory 不是 Retrieval，也不是 RAG

这是今天最需要分清的概念边界。

| 概念 | 作用 |
| --- | --- |
| Memory | 决定什么状态应该跨时间保留，并影响未来行为 |
| Retrieval | 在需要时定位并取回相关信息或状态 |
| RAG | 取回资料后辅助模型生成回答 |
| Embeddings | 把内容转成向量表示 |
| Vector Store | 存储和搜索向量的基础设施 |

RAG 可以是 memory 系统的一部分，但 RAG 本身不等于 memory。

因为 RAG 主要解决“现在要取什么资料来回答问题”，而 memory 还要解决：

- 什么值得保存？
- 保存多久？
- 什么时候返回？
- 什么时候修正？
- 什么时候忘记？
- 谁有权修改？

## 8. 两个轴：时间轴与内容轴

课件给了一个很有用的分类方式：先看时间，再看内容类型。

### 时间轴

- working / short-term：当前任务中的临时状态
- long-term / persistent：跨会话保留的长期状态

### 内容轴

长期记忆里又可以分成：

- Episodic memory：过去发生过的交互、经历和结果
- Semantic memory：稳定事实、偏好、项目知识
- Procedural memory：可复用的方法、流程、工具步骤

一个重要提醒是：

```text
scratchpad 是当前工作区状态，不应该被误认为第四种长期记忆类型。
```

也就是说，临时草稿、推理过程和当前步骤记录，不一定都应该长期保存。它们可以被总结成长期记忆，但不能无筛选地全部变成长期状态。

## 9. Memory Engineering 是生命周期管理

memory 工程不是“建一个数据库”这么简单，而是管理完整生命周期：

1. Capture：什么内容值得捕获？
2. Keep：什么内容应该持久保存？
3. Retrieve：当前任务需要返回什么？
4. Act：返回的状态如何影响下一步行动？
5. Revise：新证据出现后如何修改？
6. Forget：什么内容应该删除或失效？

我的理解：

```text
一个可用的 agent memory 系统，必须有选择地记住、有选择地取回、持续修正，并允许遗忘。
```

## 10. Memory 在 Agent Stack 中的位置

课件把 agent 系统拆成三层：

| 层级 | 问题 | memory 的位置 |
| --- | --- | --- |
| Prompt engineering | 这一次怎么问？ | 可以引用 memory，但不定义 memory |
| Context engineering | 当前窗口放什么？ | retrieval 和 memory 会决定进入上下文的内容 |
| Harness engineering | 系统如何运行？ | 工具、循环、日志、权限、生命周期和可观测性让 memory 可控 |

这解释了为什么 memory 不是单纯 prompt 技巧。

如果 memory 会影响未来行为，它就需要工程系统来支撑：存储、检索、权限、日志、更新、删除和验证。

## 11. 生态趋势：Memory 正在变成一层基础设施

课件提到了一些方向性例子：

- mem0：通用 memory layer
- Letta：stateful agent platform
- LangMem：agent memory primitives
- Zep：history + knowledge graph
- EverOS：long-term memory operating system

这些项目具体路线不同，但共同趋势是：

```text
memory 正在从单个产品功能，变成 agent 系统可复用的一层基础设施。
```

## 12. 和我的学习仓库有什么关系

我现在的学习仓库其实已经在做一种显式 memory：

- `daily/`：记录每天发生了什么、完成了什么、下一步是什么
- `notes/`：沉淀课程知识和个人理解
- `experiments/`：记录链上实验和可验证结果
- `submissions/`：保存任务提交草稿和提交记录
- `prompts/`：保存 agent 配置和协作边界
- `private/`：保存不适合公开的原始材料和敏感上下文

这套 repo 的价值不是“资料多”，而是把学习状态从聊天记录里拿出来，变成可持续更新、可审计、可复用的外部记忆。

## 13. 和 AI Concept Coach 的关系

现在的 `AI Concept Coach` 已经能做概念解释和复述反馈，但它基本还是一次性的。

如果要用今天的 memory 思路升级，它可以增加：

- 记录学习者经常混淆的概念
- 保存每次复述评分和薄弱点
- 下次优先生成针对薄弱点的练习
- 记住学习者偏好：中文为主，逐步加入英文术语
- 记录已掌握概念，避免重复训练
- 支持用户删除、导出或重置学习记录

这样它就不是一个“会回答问题的页面”，而是一个能持续跟踪理解状态的学习工具。

## 14. 安全与边界

memory 也有风险。

对学习 agent 或 Web3 agent 来说，不应该长期保存：

- API key
- token
- 私钥
- 助记词
- 钱包敏感信息
- 未经确认的个人隐私
- 会导致错误行动的过期状态

对于会调用 API、提交任务、发起链上操作的 agent，memory 必须和 human-in-the-loop 结合：

```text
Agent 可以记住背景、整理状态、提出下一步建议。
真正写入平台、提交任务、调用钱包或执行高影响操作前，必须人工确认。
```

## 15. 今日结论

Agent memory 的核心不是“让模型知道更多”，而是让 agent 能跨时间保持有用状态，并在下一步行动中正确使用这些状态。

我今天最重要的收获是：

```text
Memory = continuity + lifecycle + control.
```

如果没有 lifecycle，memory 只是堆积历史。

如果没有 control，memory 会变成风险。

如果没有和任务行动连接，memory 只是聊天体验优化。

真正的 agent memory，要能让系统记住、取回、修正、遗忘，并在用户可控的边界内支持长期协作。
